## 리베이스의 동작 원리

### 커밋 해시
커밋 해시는 Git에서 커밋을 고유하게 식별하는 값이며 Commit 객체의 내용 전체(`commit 크기\0내용`)를 SHA-1로 계산해 만든다  
Commit 객체에는 아래 값이 들어 있으므로 이 중 **하나만 달라져도** 해시는 완전히 달라진다

+ `tree`: 최상위 Tree의 해시. 즉 그 시점의 스냅샷 전체
+ `parent`: 부모 커밋의 해시
+ `author`: 변경을 처음 만든 사람과 시각
+ `committer`: 그 변경을 커밋으로 만든 사람과 시각
+ 커밋 메시지

### 리베이스란
+ 브랜치의 **베이스(갈라져 나온 시작점)를 다른 커밋으로 바꾸는** 명령
    - 브랜치의 커밋들을 새 베이스 위에서 **하나씩 다시 만든다**
    - 커밋을 "옮기는" 것처럼 보이지만 실제로는 **새 커밋을 만들고 브랜치가 새 커밋을 가리키게** 하는 것이다

```
리베이스 전                          git switch feature && git rebase main

      D ── E   ← feature                          D' ── E'   ← feature
     /                                           /
A ── B ── C    ← main                 A ── B ── C   ← main

                                      (원래 D, E는 그대로 남아 있지만
                                       어떤 브랜치도 가리키지 않는다)
```

### 리베이스가 실행되는 순서
`feature`에서 `git rebase main`을 실행하면

1. `feature`와 `main`의 공통 조상(위 그림의 A)을 찾는다
2. 공통 조상 이후 `feature`에만 있는 커밋(D, E)을 고른다. `git log main..feature`에 나오는 커밋들
3. `HEAD`를 `main`의 끝(C)으로 옮긴다 (detached HEAD 상태)
4. 고른 커밋을 오래된 것부터 하나씩 **cherry-pick 하듯** 다시 적용해 D', E'를 만든다
5. 다 끝나면 `feature` 브랜치를 마지막 새 커밋(E')으로 옮긴다

+ 다시 적용하는 방식
    - Git 2.26부터 기본 방식(merge 백엔드)은 커밋마다 **3-way 병합**으로 변경을 다시 적용한다. `cherry-pick`과 같은 방식
    - 예전 기본 방식(apply 백엔드, 지금은 `--apply`)은 커밋마다 **패치를 만들어**(`format-patch`) 적용(`am`)했다. "리베이스는 내부적으로 패치를 만든다"는 설명은 이 방식에서 나온 것

### 커밋 해시가 바뀌는 이유
+ 다시 만든 커밋은 원래 커밋과 비교해 **변경분(diff)은 같지만** Commit 객체의 값이 여러 개 달라진다
    - `parent`: 새 베이스 위에 쌓으므로 부모가 바뀐다
    - `tree`: 베이스에 있던 변경(B, C)까지 포함한 스냅샷이 되므로 **스냅샷 자체가 바뀐다**
    - `committer` 시각: 커밋을 다시 만든 시각으로 바뀐다. `author`는 그대로 유지된다
+ 그래서 "커밋 내용은 바뀌지 않는다"는 말은 **변경분은 같다**는 뜻이지, 커밋이 저장한 스냅샷이 같다는 뜻이 아니다

```
$ git cat-file -p HEAD    # 리베이스 전 E
tree d4582b305b73266ab4af934ba3b8b8c78c1c569c
parent 50ab59a899a003956f145bb8561b8fee17d55e23
author demo <demo@example.com> 1792289400 +0900
committer demo <demo@example.com> 1792289400 +0900

E

$ git rebase main
Successfully rebased and updated refs/heads/feature.

$ git cat-file -p HEAD    # 리베이스 후 E'
tree e0f7dd6493faab9fb1194ba49aeb30604401a242       ← 스냅샷이 바뀜
parent a9c3a116e7631d61af6fa8f97bab067a63567146     ← 부모가 D'로 바뀜
author demo <demo@example.com> 1792289400 +0900     ← 그대로
committer demo <demo@example.com> 1792308681 +0900  ← 다시 만든 시각

E

$ git log --format='%h %s | author %ad | committer %cd' --date=format:%H:%M main..feature
049bbf4 E | author 11:10 | committer 16:31
a9c3a11 D | author 11:00 | committer 16:31
```

> 부모 해시가 바뀌면 그 위의 자식 커밋 해시도 연쇄적으로 바뀐다. D 하나만 새 베이스로 옮겨도 그 뒤의 E는 반드시 E'가 된다.

### 리베이스에서 자동으로 빠지는 커밋
+ 새 베이스에 **이미 같은 변경이 있는 커밋**은 건너뛴다
    - 변경분이 같은지(patch-id)로 판단한다. 같은 커밋을 `cherry-pick`해 둔 경우 등
+ **병합 커밋**은 기본적으로 버리고 일반 커밋만 일렬로 다시 쌓는다
    - 병합 구조까지 유지하려면 `git rebase --rebase-merges`

### 충돌이 나면
+ 커밋을 하나씩 다시 적용하므로 **커밋마다** 충돌이 날 수 있고, 충돌이 난 커밋에서 멈춘다

```bash
# 파일을 고친 뒤
git add <파일>
git rebase --continue    # 다음 커밋으로 진행

git rebase --skip        # 이 커밋은 버리고 다음으로
git rebase --abort       # 리베이스 전 상태로 완전히 되돌리기
```

+ 리베이스 중에는 **ours와 theirs가 머지 때와 반대**다
    - 리베이스는 새 베이스(main) 위에서 내 커밋을 하나씩 적용하므로, `HEAD`(ours)는 **새 베이스 쪽**이고 theirs는 **지금 적용 중인 내 커밋**이다

```
$ git rebase main          # feature에서 실행, 같은 줄을 서로 다르게 고친 상태
CONFLICT (content): Merge conflict in f.txt
error: could not apply c95eba6... feat

$ cat f.txt
<<<<<<< HEAD
main                       ← ours  = 새 베이스(main)
=======
feature                    ← theirs = 다시 적용 중인 내 커밋
>>>>>>> c95eba6 (feat)

$ git checkout --ours f.txt   && cat f.txt   # main
$ git checkout --theirs f.txt && cat f.txt   # feature
```

### 다른 베이스로 일부만 옮기기: `--onto`
```
git rebase --onto <새 베이스> <제외할 기준> <브랜치>
```

+ `<제외할 기준>` 이후의 커밋만 골라 `<새 베이스>` 위로 옮긴다
+ `feature2`가 `feature1`에서 갈라졌는데 `feature1` 없이 `main` 위로 옮기고 싶을 때

```
git rebase --onto main feature1 feature2

리베이스 전                                리베이스 후

A ── B   ← main                           A ── B   ← main
      \                                         ├── D ── E   ← feature1
       D ── E   ← feature1                      └── F' ── G'   ← feature2
             \
              F ── G   ← feature2         feature1에만 있는 D, E는 빼고
                                          F, G만 main 위로 옮겨진다
```

### 리베이스 되돌리기
+ 원래 커밋은 삭제되지 않는다. 어떤 브랜치도 가리키지 않아 `git log`에 안 보일 뿐이다
+ 리베이스 직전 위치는 `ORIG_HEAD`에 저장되고, 이동 기록은 `reflog`에 남는다

```
$ git reflog
049bbf4 HEAD@{0}: rebase (finish): returning to refs/heads/feature
049bbf4 HEAD@{1}: rebase (pick): E
a9c3a11 HEAD@{2}: rebase (pick): D
fb2e343 HEAD@{3}: rebase (start): checkout main
2b4d35f HEAD@{4}: checkout: moving from main to feature    ← 리베이스 전 E

$ git rev-parse --short ORIG_HEAD
2b4d35f
```

```bash
git reset --hard ORIG_HEAD      # 리베이스 직후라면 가장 간단
git reset --hard HEAD@{4}       # reflog에서 리베이스 전 위치를 찾아서
git reset --hard feature@{1}    # 브랜치 reflog 기준 직전 위치
```

> `ORIG_HEAD`는 `reset`·`merge` 등 다른 명령도 덮어쓰므로 리베이스 직후가 아니면 `reflog`로 찾는 것이 안전하다.
